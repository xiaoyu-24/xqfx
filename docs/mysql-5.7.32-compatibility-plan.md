# 公司内部需求收集平台
# MySQL 5.7.32 兼容性改造与 CentOS 7/宝塔部署计划书

## 1. 项目目标

在不升级服务器 MySQL 的前提下，使平台能够在以下目标环境稳定运行：

- 操作系统：CentOS 7
- 部署方式：宝塔面板 + Nginx + Java 后端进程管理
- 数据库：MySQL 5.7.32
- 前端：Nginx 托管生产构建产物
- 后端：Spring Boot 应用独立进程运行

最终目标不是“能够启动”，而是完成数据库迁移、核心业务、附件上传、异常处理、备份恢复和重启自愈验证后再上线。

## 2. 当前基线与已知问题

当前项目情况：

- Spring Boot 3.4.5
- Hibernate ORM 6.6.13.Final
- MySQL Connector/J 9.1.0（由 Spring Boot 依赖管理引入）
- Java 编译版本 21
- Flyway 迁移版本 V1–V8
- 前端生产构建已通过，前端测试 32 项通过
- 后端测试 64 项通过，其中 MySQL Testcontainers 测试跳过 1 项

已确认的兼容性缺口：

1. Hibernate 6.6 对 MySQL 5.7.32 报告版本不受支持，当前组合没有稳定性保证。
2. `MySqlMigrationIntegrationTest` 当前使用 `mysql:8.4`，没有覆盖目标 MySQL 5.7.32。
3. 项目部署文档目前按 MySQL 8.0+ 和 Windows 路径编写，不适合直接作为 CentOS 7 宝塔部署手册。
4. 后端密码依赖环境变量，宝塔进程管理器必须显式配置，不能依赖交互式终端环境。
5. 附件目录使用环境变量配置，生产环境必须使用绝对路径并设置运行账号权限。
6. CentOS 7 已停止维护，存在系统安全风险；若无法更换系统，必须通过最小暴露面和补丁策略控制风险。

## 3. 改造原则

- 不修改 MySQL 服务器版本和现有业务数据。
- 不修改已执行过的 Flyway 历史迁移脚本；结构变更只能新增 V8、V9 等迁移。
- 所有数据库兼容性判断以 MySQL 5.7.32 实例实测为准，不以 H2 测试替代。
- 优先保持 Jakarta API 和 Spring Boot 3 技术路线，只有兼容性验证失败时才考虑更大范围降级。
- 密码、数据库地址和附件路径不写入仓库，通过宝塔环境变量或进程配置注入。
- 先在临时库/测试环境验证，再进行生产备份和部署。

## 4. 目标技术基线方案

### 4.1 后端依赖兼容性

建立兼容性验证矩阵，优先验证以下路线：

1. Spring Boot 3.3.x + Hibernate 6.5.x + Java 17/21。
2. MySQL Connector/J 固定在明确支持 MySQL 5.7 的 8.0.x 版本，优先评估 8.0.33。
3. 如果 Spring Boot 3.3.x 仍无法稳定通过 MySQL 5.7.32 集成测试，再评估 Spring Boot 3.2.x/Hibernate 6.4.x。
4. 不直接使用 Hibernate 6.6 + MySQL 5.7.32 作为生产基线。

最终版本必须满足：

- 应用启动无 Hibernate MySQL 版本不支持错误。
- Flyway V1–V8 在 MySQL 5.7.32 上全部成功。
- 全部后端测试和 MySQL 5.7.32 集成测试通过。
- 业务 API、事务、分页、乐观锁、附件读写无回归。

### 4.2 Java 与 CentOS 7

优先采用 Java 17 LTS 作为 CentOS 7 运行时，以降低旧系统上的运行时兼容风险；如果保留 Java 21，必须先在目标 CentOS 7 内核、glibc 和宝塔进程环境中完成启动验证。

若采用 Java 17，需要同步调整：

- `maven.compiler.release`
- CI/本地构建 JDK
- 宝塔 Java 运行时路径
- 启动脚本和运行手册

当前代码使用的 record、文本块等语法可在 Java 17 运行，但必须重新执行完整编译和测试。

## 5. 数据库兼容性改造内容

### 5.1 测试基线改造

- 将 Testcontainers 镜像从 `mysql:8.4` 改为 `mysql:5.7.32`。
- Docker 不可用时不能将该测试视为通过，应在发布门禁中标记为阻塞。
- 增加数据库版本断言，确保测试实际连接的是 5.7.32。
- 增加 Flyway 迁移校验、索引校验、字符集校验和关键表结构校验。

### 5.2 SQL 与迁移脚本审查

逐条审查 V1–V8：

- `DATETIME(6)`、索引、唯一键、外键在 5.7.32 上执行验证。
- 检查字符集和排序规则，统一评估 `utf8mb4`，避免 emoji 或特殊字符导致写入失败。
- 检查索引长度，确保 5.7 默认配置下不会出现索引长度超限。
- 禁止使用 MySQL 8 专属语法、窗口函数、CTE、不可移植的 JSON/DDL 特性。
- 任何新结构变更使用新的 Flyway 版本脚本，并保留回滚前置备份。

### 5.3 连接池与连接参数

针对 MySQL 5.7.32 增加并验证：

- 连接超时、读取超时和连接验证策略。
- Hikari `maxLifetime`、`keepaliveTime` 与 MySQL 连接回收时间匹配。
- 时区固定为 `Asia/Shanghai`。
- 生产环境不使用空密码，数据库账号使用最小权限。
- 如果启用 TLS，使用服务器证书配置；不以关闭安全校验作为默认解决方案。

## 6. 应用结构与部署改造

建议增加以下部署资产：

```text
deploy/
├── centos7/
│   ├── requirements-platform.service.example
│   ├── nginx-requirements.conf.example
│   ├── start-backend.sh
│   ├── health-check.sh
│   └── backup.sh
└── .env.example
```

部署结构要求：

- 前端只部署 `frontend/dist`，不部署 `node_modules`。
- 后端只部署重新构建的可执行 jar 和必要的外部目录。
- `/api` 由 Nginx 反向代理到 `127.0.0.1:8080`。
- `/api/health` 作为健康检查地址。
- 后端由 Supervisor、systemd 或宝塔 Java 进程管理器托管，配置自动重启。
- `ATTACHMENTS_ROOT` 使用例如 `/www/wwwroot/requirements-platform/uploads` 的绝对路径。
- Nginx 配置 `client_max_body_size`，且与业务允许的附件大小一致。
- 日志输出到独立目录并设置轮转，避免日志占满磁盘。

## 7. 分阶段执行计划

### 阶段一：冻结与备份

1. 冻结当前待部署代码版本，记录 Git 提交号和构建时间。
2. 清理部署包中的测试报告、临时日志、`node_modules` 和本地上传数据。
3. 备份生产数据库和附件目录，生成同批次 manifest。
4. 确认服务器 IP、SSH、宝塔权限、域名、数据库账号、附件目录和维护窗口。

交付物：版本清单、数据库备份、附件备份、部署参数表。

### 阶段二：MySQL 5.7.32 兼容性 POC

1. 启动干净的 MySQL 5.7.32 测试库。
2. 执行 Flyway V1–V8。
3. 使用目标依赖组合启动后端。
4. 执行系统、版本、需求、状态、迁移、附件和异常接口测试。
5. 执行长文本、中文、特殊字符、并发更新和失败回滚测试。
6. 记录所有 SQL、警告、慢查询和连接池异常。

通过条件：迁移成功、无版本不支持警告、核心 API 全部通过、无脏数据。

### 阶段三：CentOS 7/宝塔预发布部署

1. 安装并验证 Java 17 或已批准的 Java 21。
2. 配置数据库连接环境变量和附件目录权限。
3. 部署后端 jar，配置进程守护和自动重启。
4. 部署前端 dist，配置 Nginx `/api` 代理。
5. 执行健康检查、前端加载、系统创建、需求提交、附件上传/下载和服务重启测试。
6. 验证数据库连接断开、进程异常退出、磁盘空间不足时的告警和恢复行为。

### 阶段四：生产部署

1. 维护窗口内停止旧服务写入。
2. 执行数据库和附件双备份，并校验备份文件可读。
3. 导入部署包，配置环境变量和 Nginx。
4. 启动后端，确认 Flyway 校验通过。
5. 访问 `/api/health`，再进行最小业务验收。
6. 观察日志、连接池、磁盘和数据库连接至少一个业务周期。

## 8. 验收标准

### 必须通过

- MySQL 5.7.32 集成测试 1 项实际执行并通过，不能跳过。
- 后端全量测试 0 失败、0 错误。
- 前端测试 32 项通过，生产构建通过。
- Flyway V1–V8 成功，数据库版本记录正确。
- `/api/health` 返回 `{"status":"UP"}`。
- 系统、协助人、版本、需求、状态、迁移、附件上传/下载全部成功。
- 非法枚举返回 400，未知后端资源返回 404。
- 服务重启后数据和附件仍可访问。
- 备份恢复后系统、需求和附件可用。

### 不允许带病上线

- 数据库迁移失败或出现 checksum 不一致。
- Hibernate 报 MySQL 版本不支持且未经过风险批准。
- 附件目录无写权限或使用相对临时目录。
- 数据库密码写入 Git、前端 dist 或公开日志。
- 进程无自动重启和健康检查。
- 生产库没有可验证的回滚备份。

## 9. 回滚方案

### 应用回滚

保留上一版 jar 和前端 dist，停止当前进程后恢复上一版本并重新执行健康检查。

### 数据库回滚

Flyway 不对已执行迁移自动回滚。任何新增迁移前必须完成数据库备份；如果迁移涉及破坏性变更，必须先提供反向迁移脚本或使用备份恢复。

### 附件回滚

应用版本和附件目录必须按同一批次标识管理，不能只回滚数据库而保留不匹配的附件目录。

## 10. 当前结论

当前代码可以进入兼容性改造阶段，但尚未达到 MySQL 5.7.32 生产部署准入标准。下一步应先完成“依赖基线调整 + MySQL 5.7.32 集成测试”，确认通过后再编写宝塔实际配置并部署。

部署前需要确认：

1. 是否允许将 Java 运行时调整为 Java 17。
2. MySQL 5.7.32 的数据库名、账号、密码和权限。
3. 宝塔服务器的 Java 进程托管方式。
4. 生产附件目录、域名和 Nginx 端口。
5. 维护窗口和备份保留策略。

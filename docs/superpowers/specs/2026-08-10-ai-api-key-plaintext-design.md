# AI API Key 明文存储改造设计

## 背景

当前 AI 配置使用 `AI_ENCRYPTION_KEY` 对 API Key 执行 AES-GCM 加密。部署环境未提供密钥、密钥格式错误或密钥与历史数据不一致时，配置保存、连接测试或智能导入会失败。系统已经具备登录鉴权，用户决定移除 API Key 加密，并在升级时清空旧 Key 后由管理员重新填写。

## 目标

- 后端不再依赖 `AI_ENCRYPTION_KEY`。
- API Key 以明文保存在数据库中，智能导入直接读取该值调用 AI 服务。
- 升级时清空所有历史密文，避免把密文误当作可用 Key。
- AI 配置列表仍只返回掩码，不向浏览器返回完整 Key。
- 保持现有权限边界：AI 配置仅管理员可管理，智能分析仅登录用户可调用。

## 非目标

- 不修改 AI 服务协议、模型请求格式或智能导入的字段识别规则。
- 不调整登录、角色或会话机制。
- 不尝试恢复历史加密 Key。
- 不在前端、本地存储、日志或响应中暴露完整 Key。

## 方案

### 数据库

新增 Flyway 迁移：

1. 将 `ai_config.api_key_encrypted` 改名为 `api_key`，保持 `VARCHAR(1000)` 和可空约束。
2. 将所有已有记录的 `api_key` 更新为 `NULL`。

项目目标数据库为 MySQL 5.7.32，因此迁移使用兼容的 `CHANGE COLUMN` 语法，不使用 MySQL 8 才支持的字段重命名语法。

### 后端模型与服务

- `AiConfigEntity` 将字段及访问方法改为 `apiKey`。
- 创建或更新配置时，对非空 API Key 去除首尾空白后直接保存。
- 请求未携带 API Key 或只携带空白时，保留数据库中的现有值，维持当前编辑行为。
- 连接测试和智能分析直接读取 `apiKey`；非空时添加 `Authorization: Bearer <key>`。
- 删除 AES、Base64、随机 IV、加密密钥注入和相关错误分支。
- 配置响应继续使用前后各四位的掩码；短 Key 显示 `****`。

### 配置与文档

- 从 `application.yml` 删除 `app.ai.encryption-key`。
- 从部署示例和部署文档删除 `AI_ENCRYPTION_KEY`。
- 文档明确 API Key 以明文存储，数据库账号、备份和服务器文件权限必须受控。

## 数据流

1. 管理员登录后在 AI 配置页填写新 Key。
2. 前端通过现有 AI 配置接口提交 Key。
3. 后端将 Key 明文写入 `ai_config.api_key`。
4. 配置查询接口仅返回掩码。
5. 登录用户执行智能导入时，后端读取激活配置的 Key，并仅在服务端请求 AI 提供方。

## 错误处理

- 未配置 Key 时仍允许调用不需要鉴权的兼容服务；需要 Key 的服务会返回其原始 HTTP 错误状态。
- 服务地址、模型名、连接超时和 AI 响应解析继续使用现有错误提示。
- 迁移完成后旧 Key 为空，管理员必须重新填写才能访问需要鉴权的 AI 服务。

## 测试与验收

采用测试驱动实现：

1. 先增加失败测试，证明未配置 `AI_ENCRYPTION_KEY` 时可以保存并读取 API Key。
2. 验证配置响应只包含掩码，不包含完整 Key。
3. 验证更新时空白 API Key 不会覆盖已有值。
4. 验证智能分析和连接测试取得的是明文 Key。
5. 运行后端测试与 Maven 构建。
6. 检查 Flyway 迁移兼容 MySQL 5.7.32，并确认迁移会清空旧值。

验收标准：部署环境不设置 `AI_ENCRYPTION_KEY`，管理员重新填写并激活 AI 配置后，连接测试和 AI 智能导入能够使用该 Key，任何配置查询响应均不返回完整 Key。

## 风险

取消加密意味着数据库读取权限、数据库备份访问权限或服务器入侵都可能直接暴露 API Key。该风险由用户明确接受，部署时需限制数据库账号、备份文件和服务器访问权限。

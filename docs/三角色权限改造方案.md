# 三角色权限改造方案

> 版本：v1.0 ｜ 日期：2026-08-09 ｜ 状态：已确认，待实施
>
> 配套设计稿：[人员管理页视觉设计稿.html](./人员管理页视觉设计稿.html)

## 1. 背景与目标

当前系统仅有"管理员 / 普通用户"两类账号（`users.admin_role` 布尔字段），且后端除人员、字典、AI 配置三个管理接口外，**没有任何资源级权限校验**——任何登录用户均可编辑、删除他人需求，甚至管理系统与版本。

本次改造将角色扩展为三类，并将权限校验落实到后端接口层：

| 角色 | 定位 |
|---|---|
| 普通用户（USER） | 仅提交与跟进自己填写的需求 |
| 需求处理员（HANDLER） | 处理全部需求，可管理 系统/版本，可担任系统负责人 |
| 管理员（ADMIN） | 含需求处理员全部权限，另管人员、字典、AI 配置（维持现状） |

## 2. 已确认的决策（2026-08-09）

1. 普通用户**不能**担任需求处理人；系统负责人即需求的处理人，仅需求处理员和管理员可担任系统负责人/协助人。
2. 普通用户仅可删除自己填写且处于**「草稿 / 待评估」**状态的需求；其他阶段不可删除，也不提供"撤回"功能。
3. 普通用户的需求列表**仅可见自己填写的需求**。
4. 普通用户**完全不可见**信息通知。
5. 需求处理员**可以**管理系统/版本。
6. 普通用户**不可见**待办工作台，仅可见「填写需求」和「需求列表」两个页面。

## 3. 最终权限矩阵

| 能力 | 普通用户 | 需求处理员 | 管理员 |
|---|:-:|:-:|:-:|
| 填写需求 / 存草稿 | ✅ | ✅ | ✅ |
| 编辑自己填写的需求 | ✅ | ✅ | ✅ |
| 删除自己的需求 | 仅「草稿 / 待评估」 | 全部 | 全部 |
| 编辑 / 删除他人需求 | ❌ | ✅ | ✅ |
| 更新进度 / 变更状态 | ❌ | ✅ | ✅ |
| 担任系统负责人 / 协助人 | ❌ | ✅ | ✅ |
| 需求列表数据范围 | 仅自己填写的 | 全部 | 全部 |
| 系统 / 版本管理 | ❌ | ✅ | ✅ |
| 待办工作台 | ❌ | ✅ | ✅ |
| 信息通知 | ❌ | ✅ | ✅ |
| 人员管理 / 字典管理 / AI 配置 | ❌ | ❌ | ✅ |

## 4. 后端改造

### 4.1 数据模型与迁移

- `users.admin_role`（BOOLEAN）→ `users.role`（VARCHAR(20)，取值 `USER` / `HANDLER` / `ADMIN`）。
- 存量数据映射：`admin_role = 1 → ADMIN`；`admin_role = 0 → HANDLER`（保证现有人员权限不缩水）。
- 新建用户默认角色为 `USER`。
- 接口出参 `UserResponse.admin: boolean` → `role: string`，前端同步适配。

### 4.2 AuthInterceptor（路径级拦截）

- 保留现有管理员专属前缀：`/api/users`、`/api/ai-config`、`/api/dictionaries`（`/active` 例外不变）。
- 新增普通用户（USER）拦截规则，禁止访问：
  - `/api/dashboard/**`（待办工作台）
  - `/api/notifications/**`（信息通知）
  - `/api/systems/**`、`/api/system-versions/**`（系统/版本管理）

### 4.3 RequirementService（资源级校验，当前完全缺失，必须新增）

| 操作 | 普通用户规则 |
|---|---|
| 需求列表 / 详情查询 | 自动附加 `creator_id = 本人` 过滤，查他人需求返回 403/404 |
| 编辑需求（含草稿保存） | 仅 `creator = 本人` |
| 删除需求 | `creator = 本人` 且状态 ∈ {草稿, 待评估}，否则 403 |
| `POST /{id}/progresses`（更新进度） | 禁止，仅 HANDLER / ADMIN |
| `PATCH /{id}/assignee`（指派） | 禁止，仅 HANDLER / ADMIN |
| 附件上传 / 删除 | 跟随需求编辑权限（仅自己的需求） |

### 4.4 SystemService

- 系统负责人、协助人的可选账号范围限定为 `role ∈ {HANDLER, ADMIN}`。
- 人员角色由 HANDLER/ADMIN 降级为 USER 时，若其仍担任某系统负责人/协助人，需强制先完成变更（或拦截降级并提示）。

### 4.5 NotificationService

- 不向 USER 角色产生、投递任何通知；通知查询接口对 USER 直接拦截（见 4.2）。

### 4.6 UserService

- 人员 CRUD 支持三角色；保留"最后一名启用管理员不可降级/停用"的现有保护。

## 5. 前端改造

1. `useAuth`：`isAdmin` 布尔 → `role` 三态（`USER` / `HANDLER` / `ADMIN`）。
2. `App.vue` 菜单：`pages` 元数据由 `adminOnly` 改为 `roles` 数组，按角色过滤可见菜单：
   - USER：填写需求、需求列表
   - HANDLER：待办工作台、填写需求、需求列表、系统管理
   - ADMIN：全部
3. 需求列表 / 详情页：编辑、删除、更新进度按钮按"角色 + 是否本人 + 需求状态"条件渲染；普通用户对非「草稿/待评估」需求**隐藏**删除按钮（而非置灰，避免误导）。
4. 人员管理页：按设计稿实现——角色开关改为三选卡片、角色列三色标签、顶部角色权限说明卡片。
5. 路由守卫：普通用户直接访问受限路由时重定向至需求列表。

## 6. 界面设计要点（见设计稿 HTML）

- **三张角色说明卡片**（页面顶部）：展示各角色权限边界与人数统计。
- **人员列表**：角色列三色胶囊标签（管理员=蓝 / 需求处理员=橙 / 普通用户=灰）；筛选条支持"账号/姓名、角色、状态"。
- **新增/编辑弹窗**：角色三选卡片 + 角色变更影响提示条。
- **三角色菜单对比区**：呈现三种角色登录后的侧边栏差异，作为开发对照基准。

## 7. 实施顺序建议

1. 数据库迁移（`role` 字段 + 存量映射）
2. 后端：AuthInterceptor 角色维度 + RequirementService 属主/状态校验 + SystemService 负责人范围校验 + 通知屏蔽
3. 前端：`useAuth` 三态化 → 菜单/路由过滤 → 需求页按钮显隐 → 人员管理页
4. 回归验证：三种角色分别登录，核对菜单、数据范围、越权接口返回 403

## 8. 风险与注意事项

- **存量普通用户将全部变为需求处理员**（权限不变），新增账号默认普通用户——后续人员角色需管理员逐一核对调整。
- 普通用户不可见通知后，其需求被处理完成时**无任何触达渠道**；如后续反馈体验问题，可考虑放开"仅与自己需求相关"的通知。
- 后端校验是唯一可信防线；前端隐藏菜单/按钮仅作用户体验，不可作为安全措施。
